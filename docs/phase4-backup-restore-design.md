### 1.2 الخلاصة الجوهرية للنطاق

> **النظام بلا أي حالة على القرص خارج قاعدة البيانات عدا إعدادات البيئة.**
> نسخة متسقة من `custom.db` + Manifest يغطيان **100% من بيانات النظام** (المستخدمون، التقارير بمحتوى ملفاتها الكامل، المجموعات، WorkflowHistory، AuditLog). الإعدادات تُوثق كقيم غير سرية في Manifest + إجراء تشغيلي منفصل للأسرار.

### 1.3 ما لا يُدخل في النسخة (وضوح كامل)

- **`.env` كاملًا**: يحوي مسارات وقد يحوي أسرارًا مستقبلًا. بديله: تسجيل **القيم غير السرية** في Manifest (`businessTzOffsetMinutes`, `appVersion`, `schemaVersion`) + **بصمة fingerprint لملف الإعدادات** (SHA-256 لقيمه بعد استبعاد الأسرار) للكشف عن انحراف البيئة بعد الاستعادة. تثبيت الأسرار إجراء تشغيلي يدوي موثق (قسم 13.4).
- أي مسارات كود/بناء/سجلات (بنود 6–9 في الجدول).
- **ملاحظة أمنية مكتشفة**: `/api/setup` ينشئ مديرًا افتراضيًا (admin/admin123) إذا كانت قاعدة المستخدمين فارغة — بعد استعادة نسخة قديمة أو فارغة يجب فحص هذا السلوك (مغطى في قسم 7 «sanity check» وقسم 16 تهديدات).

### 1.4 ملاحظة تخزين حرجة تحتاج قرارًا (D-2)

`backups/` حاليًا **داخل مجلد المشروع ومتتبع بـ git** (يظهر في git status كملف معدّل). المفارقة الموثقة:
- وضعه **خارج** المشروع كان سبب فقدان نسخة pre-phase3 عند نقل بيئة العمل (`/home/z/` مُسحت، المشروع بقي).
- إبقاؤه **متتبعًا في git** يلوث اللقطات بملفات ثنائية متغيرة.

**التوصية**: إبقاء النسخ داخل المشروع (`backups/` — يبقى ضمن مساحة العمل الدائمة) + **إيقاف تتبع ملفات `.db/.manifest.json` في git مستقبلًا فقط** (إضافة .gitignore للأمام — ليست إعادة كتابة تاريخ ولا حذف لقطات). قرار D-2.

## القسم 2 — النسخ المتسق: VACUUM INTO (القرار المدعوم بالتحليل)

### 2.1 لماذا لا تُنسخ ملفات DB مباشرة (filesystem copy)

مع WAL: قد يكون ملف `.db` الرئيسي **متخلفًا** عن أحدث كتابة (المعاملات في `-wal`)، ونسخ `.db`+`-wal`+`-shm` معًا أثناء التشغيل قد يلتقط الملفات في لحظات مختلفة ⇒ **نسخة ممزقة غير قابلة للفتح أو أسوأ: قابلة للفتح ببيانات ناقصة بصمت**. مرفوض من الأساس.

### 2.2 المقارنة بين الخيارين الآمنين

| المعيار | `VACUUM INTO` | SQLite Backup API (sqlite3_backup) |
|---|---|---|
| اتساق snapshot | قراءة متسقة كاملة (معاملة قراءة ضمنية) | متسق صفحة-بصفحة |
| يتوفر في `bun:sqlite` | **نعم — مثبت عمليًا في المشروع** (backup-35.ts نجح في 3.5A) | غير معرّض في bun:sqlite (يتطلب native add-on) |
| فحص سلامة أثناء النسخ | يتحقق من بنية الصفحات أثناء الكتابة | نسخ خام للصفحات |
| نتيجة مضغوطة | نعم (يعيد بناء الملف بلا فراغات) | نسخ الحجم الكامل بما فيه الفراغات |
| تصادم مع Prisma | **لا** (لا يطلب checkpoint — القيد الموثق سابقًا: wal_checkpoint(TRUNCATE) يتصادم مع Prisma) | يتطلب إعادة محاولة عند قفل |
| الأداء على 1.4MB (والمتوقع عشرات MB) | مئات الميلي ثانية | مماثل |

### 2.3 القرار

**`VACUUM INTO` هو الطريقة الأنسب لهذا المشروع** — وهو النمط المعتمد والمجرَّب بالفعل:
1. يُنشأ ملف النسخة باسم فريد خادمي (الملف يجب ألا يكون موجودًا مسبقًا — تضمنه التسمية بالطابع الزمني + معرف عشوائي).
2. فورًا بعد الإنشاء: `PRAGMA integrity_check` **على النسخة نفسها** (فتح readonly) — النتيجة تُسجل في Manifest.
3. SHA-256 للملف يُحسب ويُسجل.
4. فشل أي خطوة ⇒ حذف الملف الجزئي + حدث `BACKUP_FAILED` (قسم 6) — لا يبقى أي أثر مضلل.

ملاحظة تشغيلية: النسخ تُنشأ **دون إيقاف النظام** (قراءة متسقة لا تحجب الكتابة في WAL) — وينطبق ذلك على نسخ pre-restore أيضًا.

│                                                                       │

│    │  تبويب «النسخ الاحتياطي» في /admin                              │

│      ifrs-full-<UTC>.manifest.json                                 │

│    var/recovery/                ⬅ السجل التشغيلي الخارجي           │

قواعد صارمة للمسارات:
- **أسماء الملفات تُولَّد خادميًا حصرًا** — المستخدم لا يحدد أي filesystem path أبدًا (الرفع يُعاد تسميته فورًا `staged-<id>.db`).
- الوصول للملفات عبر **معرف backupId فقط** (نمط `^[a-z0-9-]+$` — يرفض `..` و `/` وهلمّجرًا) + تحقق `path.resolve()` يقع حتمًا داخل مجلد النسخ (دفاع ثاني).
- المجلدات خارج `public/` كليًا — التنزيل عبر API فقط بفحص صلاحية وتدقيق.
- أذونات الملفات `0600` والمجلدات `0700`.

## القسم 4 — صيغة Manifest

كل نسخة يصاحبها `*.manifest.json` مكتوب **بعد** اكتمال النسخة وفحصها (النسخة بلا Manifest = غير صالحة ولا تُعرض في القائمة). الحقول:

```json
{
  "manifestVersion": 1,
  "backupId": "bk-20260920T060000Z-x7k2m9",
  "kind": "manual | pre-restore",
  "createdAt": "2026-09-20T06:00:00.000Z",
  "createdBy": { "id": "cuid...", "username": "admin" },

  "application": {
    "appVersion": "1.0.0",
    "schemaVersion": "v4-phase3.5B",
    "schemaFingerprint": "sha256:...",
    "migrations": { "tracked": false, "applied": [] }
  },

  "database": {
    "filename": "ifrs-full-20260920T060000Z-x7k2m9.db",
    "sizeBytes": 1400832,
    "pageSize": 4096,
    "sha256": "64-hex...",
    "integrityCheck": "ok",
    "journalModeAtBackup": "wal"
  },

  "counts": {
    "users": 1, "groups": 0, "reports": 0,
    "auditLog": 0, "workflowHistory": 0
  },

  "dataRange": {
    "oldestCreatedAt": "2026-09-19T20:00:00.000Z",
    "newestUpdatedAt": "2026-09-20T05:59:00.000Z",
    "minPeriodEnd": null, "maxPeriodEnd": null
  },

  "environment": {
    "businessTzOffsetMinutes": 180,
    "configFingerprint": "sha256-of-non-secret-env-values"
  }
}
```

- **schemaFingerprint**: hash لجرد (جدول، عمود، ترتيب) مستخرج من `sqlite_master`/`PRAGMA table_info` — يكشف «هل هذه قاعدتنا؟» وأي فرق مخطط بغض النظر عن أرقام إصدارات يدوية.
- **schemaVersion**: اسم قابل للقراءة البشرية يثبته الكود مع كل تغيير مخطط.
- **migrations**: يتحول إلى `{tracked: true, applied: ["20260101_init", ...]}` بعد اعتماد خطة القسم 18.
- الحدود (الحد 10 من تعليمات المستخدم) كلها موجودة: backupId, createdAt, createdBy, application/schema version, database filename, database size, checksum SHA-256, integrity result, counts الأساسية (+ dataRange لإثراء شاشة التأكيد — بند 14).

## القسم 5 — الأكواد الرقابية + السجل التشغيلي الخارجي (Operational Recovery Log)

### 5.1 أكواد AuditLog الجديدة (داخل قاعدة البيانات — للعرض داخل التطبيق)

| الكود | متى | metadata (مقتصدة — لا مسارات ولا محتويات) |
|---|---|---|
| `BACKUP_CREATED` | نجاح إنشاء | backupId, kind, sizeBytes, sha256(أول 12), counts |
| `BACKUP_FAILED` | فشل أي خطوة | stage (vacuum/integrity/manifest), reason |
| `RESTORE_STARTED` | بدء execute | backupId (أو stagedId), source (upload/local), typed confirm مؤكد |
| `RESTORE_COMPLETED` | نجاح + تحقق | backupId, durationMs, preRestoreBackupId, postChecks |
| `RESTORE_FAILED` | فشل | stage, reason, rolledBack (bool), preRestoreBackupId |
| `RESTORE_ROLLED_BACK` | نجح الـ rollback | preRestoreBackupId, reason |

هذه أكواد **تكميلية** للسجل الرقابي القائم (append-only نفسه، نفس Sanitizer، نفس الصلاحيات — المدير فقط).

### 5.2 المشكلة التي أشار إليها المستخدم بدقة (وتُقبل كما هي)

> «إذا تمت استعادة قاعدة أقدم، فإن AuditLog الموجود داخل قاعدة البيانات نفسها قد يعود إلى الماضي ويختفي منه سجل عملية Restore» — **صحيح تمامًا**: الأحداث RESTORE_* المكتوبة في DB القديمة تختفي عند الاستبدال، وأحداث post-restore تُكتب في DB الجديدة فقط.

### 5.3 التصميم: سجل استرجاع تشغيلي خارج قاعدة البيانات

- **الملف**: `var/recovery/recovery-log.jsonl` — سجل أسطر JSON (append-only) **غير متجاوز لأي استبدال DB** (ملف مستقل لا يمسه الاستبدال).
- **الكتابة**: كل حدث من جدول 5.1 يُكتب **مرتين**: AuditLog (best-effort داخل DB) + recovery-log.jsonl (مصدر الحقيقة للأدلة). كتابة JSONL تسبق الرد على المستخدم؛ فشل كتابة JSONL لا يفشل العملية لكنه يُنذر في الاستجابة ويُسجل في dev.log.
- **صف JSONL واحد**:

```json
{"ts":"2026-09-20T06:05:11.234Z","event":"RESTORE_COMPLETED","backupId":"bk-...","actorId":"...","actorUsername":"admin","ip":"...","manifestSummary":{"createdAt":"...","sha256Short":"abc123","counts":{"users":8,"reports":23}},"preRestoreBackupId":"bk-...","result":"success","appVersion":"1.0.0","schemaVersion":"v4-phase3.5B"}
```

- **القراءة**: يُعرض آخر N حدثًا (مثلاً 50) في تبويب النسخ الاحتياطي بعنوان «سجل الاسترجاع التشغيلي (خارج قاعدة البيانات — يبقى بعد الاستعادة)» — صلاحية `manageBackups` نفسها. لا تعديل/حذف عبر أي API.
- **الحماية**: نفس أذونات 0700/0600؛ لا يُكتب فيه أي سر أو مسار داخلي (نفس Sanitizer).
- **لماذا JSONL لا جدول في DB ثانية؟** لأن استبدال DB هو الحدث ذاته — أي تخزين داخل DB المستبدلة ينكسر بالتعريف. الملف الخارجي هو الحل الوحيد المتسق، ويتحمل النسخ الخارجي مستقبلًا (قسم 19) كأدلة استرجاع كاملة.

## القسم 6 — نموذج الصلاحيات

### 6.1 مفتاحان جديدان (لا مفتاحًا واحدًا) — قرار D-5

| المفتاح | يمنح | افتراضي user | المدير (role=admin) |
|---|---|---|---|
| `manageBackups` | عرض القائمة+Manifests، **إنشاء** نسخة، تنزيل، قراءة سجل الاسترجاع | false | ضمنيًا بالدور (نفس نمط assignWorkflow/reopenReport) |
| `restoreDatabase` | رفع نسخة للتحقق، **تنفيذ الاستعادة** الكاملة | false | ضمنيًا بالدور |

**مبرر الفصل**: إنشاء/تنزيل نسخ عملية متكررة منخفضة الخطر نسبيًا؛ الاستعادة **عملية إتلافية للبيانات** بإمكانية الرجوع لماضٍ كامل — فصلها يسمح بمنح الأولى لمشغل تشغيلي والثانية مقيّدة أدوارًا أعلى، ويجعل كل تدقيق أوضح. (إن فضّل المستخدم مفتاحًا واحدًا `manageBackups` يُمنح كل شيء — بسيط التراجع، لكن التوصية اثنان.)

**موضحًا صراحة** (بند 5): لا تُشتق أي صلاحية نسخ/استعادة ضمنيًا من `settings` أو من كون المستخدم مديرًا **إلا** عبر قاعدة الدور نفسها المطبقة على بقية المفاتيح — أي أن `settings=true` وحدها **لا** تمنح شيئًا هنا.

### 6.2 Server-side حصرًا

كل العمليات (إنشاء/تنزيل/رفع/استعادة) تنفذ في الخادم عبر APIs محمية بـ `requireAuth` + فحص المفتاح + `writeAudit`. لا يُرسل للعميل أي مسار قرص — الاستجابات تحمل backupId/أسماء منطقية/أحجام/حقول Manifest فقط.

### 6.3 حدود إضافية

- **Rate limit**: إنشاء نسخة لا يزيد عن مرة كل 60 ثانية (400 BACKUP_RATE_LIMITED) — يمنع استنزاف القرص بالتكرار.
- **SoD تشغيلي مقترح** (لا إلزامي): تدقيق RESTORE يظهر من نفّذه ووقته — أي فصل أدوار أعمق (من يوافق على الاستعادة مقابل من ينفذها) يؤجل لقرار مستقبلي إن طلبه المستخدم.

## القسم 7 — خط التحقق قبل الاستعادة (Validation Pipeline)

يُنفذ **على نسخة في `var/restore-staging/` حصرًا** — قاعدة التشغيل لا تُلمس إطلاقًا في هذا الخط. الترتيب الإلزامي (أي فشل يوقف ويحذف الملف المرحلي ويبلّغ بخطأ structured):

| # | الفحص | التفاصيل | كود الفشل |
|---|---|---|---|
| 1 | Magic header | أول 16 بايت = `SQLite format 3\0` | `NOT_SQLITE` |
| 2 | الحجم | > 512 بايت، ≤ الحد الأقصى (افتراضي 200MB، قابل للتهيئة) | `FILE_TOO_LARGE/FILE_EMPTY` |
| 3 | الفتح الآمن | فتح readonly على النسخة المرحلية + `PRAGMA integrity_check` = ok | `CORRUPT_DB` |
| 4 | الجداول المطلوبة | الخمسة كلها موجودة: User, Group, Report, WorkflowHistory, AuditLog | `MISSING_TABLES` |
| 5 | توافق المخطط | مقارنة schemaFingerprint | حسب سياسة D-3 أدناه |
| 6 | الـ checksum | إذا ورد Manifest: مطابقة SHA-256؛ إن فشلت ⇒ رفض قاطع | `CHECKSUM_MISMATCH` |
| 7 | هل هي قاعدتنا؟ | fingerprint مطابق لأحد الإصدارات المعروفة أو مؤهل بالسياسة | `FOREIGN_DB` |
| 8 | Sanity أعمال | عدد المستخدمين ≥ 0 منطقي؛ **إن كانت users=0** يُنذر صراحة «الاستعادة ستُفعّل شاشة الإعداد الأولي (admin افتراضي)» | `SANITY_WARNING` |

### 7.1 سياسة التوافق مع نسخة أقدم Schema (قرار D-3 — لا يُحسم بالكود قبل الموافقة)

- **الخيار أ — الرفض**: أمان أقصى، لكنه يجعل النسخ القديمة عديمة القيمة بعد أي تطور مخطط. غير موصى به وحده.
- **الخيار ب — القبول ثم migrations**: مرن، لكنه **يتطلب** اكتمال خطة القسم 18 أولًا (دون `_prisma_migrations` لا توجد آلية موثوقة للترحيل بعد الاستبدال).
- **الخيار ج — سياسة إصدارات معروفة (التوصية المرحلية)**: تُقبل فقط البصمات الموجودة في قائمة «الإصدارات المعروفة» المشفرة في الكود (حاليًا: بصمة v4-phase3.5B الحالية + بصمة pre-3.5A المحفوظة لدينا). قبل وجود migrations: **الرفض الافتراضي لأي بصمة غير معروفة** مع رسالة تشرح السبب. بعد اعتماد القسم 18: الانتقال إلى (ب) — قبول أقدم مع **نافذة موافقة صريحة** في الواجهة تعرض «نسخة بمخطط أقدم (X) — سيُنفذ `migrate deploy` بعد الاستبدال» وربما خطوة إضافية منفصلة للتأكيد.

## القسم 8 — تسلسل الاستعادة الكامل (Restore Sequence)

مراحل المستخدم العشر حرفيًا، بلا أي اختصار:

```
 المستخدم(restoreDatabase)      الخادم                        القرص
      │                          │                              │
 ① Upload/Select ────────────────▶ استلام/اختيار backupId      │
      │                           ├─(رفع)──▶ staging/staged-<id>.db   (لا ثقة بالاسم الأصلي)
 ② Validate ─────────────────────▶ خط التحقق الثماني (قسم 7)   │
      ◀── تقرير تحقق كامل ────────┤                              │
 ③ Preview ──────────────────────▶ قراءة counts+dataRange من   │
      ◀── «ستفقد X تقريرًا/Y مستخدمًا الحاليين مقابل Z/W...» ──┤
 ④ Confirm: كتابة RESTORE ──────▶ فحص الكلمة + توكن جلسة حديث  │
 ⑤ Pre-Restore Backup ──────────▶ VACUUM INTO من قاعدة التشغيل │
      │                           │   + integrity + manifest (kind=pre-restore)
      │                           │   ⬅ إلزامي — لا يوجد bypass في الواجهة ولا API
 ⑥ Maintenance Mode ─────────────▶ رفع العلم + انتظار إنهاء   │
      │                           │   الكتابات الجارية (قسم 9)  │
 ⑦ Restore ──────────────────────▶ db.$disconnect()            │
      │                           ├─ نقل القديمة إلى staging/replaced-<ts>.db
      │                           ├─ نقل المرحلية إلى db/custom.db (rename ذري)
      │                           ├─ إزالة -wal/-shm المتبقية (بعد انقطع الحائزين)
 ⑧ Integrity Verification ──────▶ فتح جديدة readonly: integrity │
      │                           │   + جداول + counts vs manifest│
      │   (فشل؟ ⇒ Rollback تلقائي: إعادة replaced → pre-restore │
      │    تُستعاد مكانها + RESTORE_ROLLED_BACK — قسم 10)       │
 ⑨ Restart/Reconnect ───────────▶ إعادة إنشاء PrismaClient     │
      │                           │   (+ تدوير NEXTAUTH_SECRET   │
      │                           │    وإعادة تشغيل العملية — D-7، قسم 13)
 ⑩ Completion ──────────────────▶ رفع الصيانة + كتابة الأحداث │
      ◀── تقرير نتيجة نهائي ─────┤   RESTORE_COMPLETED (DB+JSONL)
                                  ▼                              ▼
```

- **فشل التحقق قبل ⑤ ⇒ قاعدة التشغيل لم تُلمس إطلاقًا** (بند 6 حرفيًا).
- التنفيذ عمليًا endpoints اثنان: `restore/validate` (①②③) ثم `restore/execute` (④–⑩) بمعامل `stagedUploadId` أو `backupId` + كلمة التأكيد. الحجم الحالي (MB) يجعل التنفيذ الكامل خلال ثوانٍ؛ الحد الأقصى للتدفق: 120 ثانية ثم فشل منظم مع بقاء ما تم بأمان (pre-restore موجود، العلم يُرفع دائمًا في finally).
- كل خطوة تفشل ⇒ **finally يضمن**: رفع الصيانة، مسح المرحلي، كتابة حدث الفشل في JSONL — لا بقاء في حالة معلقة صامتة.

## القسم 9 — Maintenance Mode (تصميم مع Next.js/Prisma)

### 9.1 الخطر المحدد

استعادة أثناء كتابة مستخدمين = فقدان تلك الكتابات أو تلف ملف مستبدل تحت قارئ نشط (المقبض القديم يشير إلى inode يتيم — الكتابة «تنجح» وتختفي). هذا الخطر يجب حجبه تصميميًا لا تشغيليًا.

### 9.2 الآلية

1. **علم ملفي**: `var/maintenance.json` `{enabled, reason, startedAt, by}` — يقرأه كل handler كتابة عبر دالة حراسة واحدة `assertWritable()` تُستدعى في **كل** مسارات POST/PUT/PATCH/DELETE الحالية (reports، workflow، assignments، due-date، users، groups، audit لا يكتب إلا النظام…) — إضافة حراسة مركزية تمر على القائمة الموجودة (جرد صريح في التنفيذ: عدد endpoints الكتابة الموجودة اليوم = 11).
2. الطلب المرفوض: `503 {error: "MAINTENANCE_MODE", retryAfter}` — **قراءة** (GET) تبقى مسموحة طول النافذة (WAL يمنح قراءة متسقة بلا تعارض) وتُحجب فقط لحظة التبديل (ثوانٍ).
3. **تصريف الكتابات الجارية**: عداد in-flight writes في عملية الخادم يزداد داخل assertWritable وينقص بعد إتمام المعاملة؛ مرحلة ⑥ تنتظر العداد=0 بحد أقصى 30 ثانية ثم تفشل بأمان (لا فرض قطع منتصف معاملة SQLite — transactions إما تكتمل أو تتراجع ذاتيًا، لكننا لا نبدأ التبديل حتى لا تكون هناك معاملة نشطة نعرف عنها).
4. **الطلبات التي وصلت قبل رفع العلم لكنها لم تبدأ كتابتها بعد**: حراسة assertWritable تمنعها عند أول محاولة كتابة فعلية — نافذة العرقلة ضئيلة ومغطاة بالعداد.
5. **واجهة المستخدمين**: `GET /api/system/status` (عام، بلا بيانات حساسة) يعيدها الشريط العلوي بالاستطلاع كل 15 ثانية أثناء ظهور أي 503 + عند فتح الصفحة؛ رسالة عربية: «النظام في وضع الصيانة لعملية استعادة — التعديلات معلقة مؤقتًا، بياناتك آمنة». عند 503: toast فوري + تعطيل أزرار الكتابة.
6. **/login وsessions** تبقى تعملان (قراءة) — لكن راجع القسم 13: بعد التدوير لا جلسة قديمة تعمل أصلًا.
7. **نقطة صدق توثق**: هذا التصميم يحمي داخل عملية الخادم الواحدة (الحالة هنا: عملية next dev واحدة على 3000). لا يحل الطلبات من عمليات خارجية على نفس DB (لا وجود لأي عملية أخرى تكتب اليوم — الجرد يؤكد). يوثق كحد نطاق.

### 9.3 ما لا تفعله الصيانة

لا توقف الخادم ولا تغير المسارات — يستطيع المدير تنفيذ العملية كلها من الواجهة لأن حراسة الكتابة **تستثني مسارات backup/restore نفسها** (قائمة استثناء صريحة قصيرة مدققة: لا يجوز أن تحجب الصيانة أدوات إدارتها).

## القسم 10 — التحقق بعد الاستعادة والـ Rollback التلقائي

### 10.1 الفحوص (مرحلة ⑧)

1. `PRAGMA integrity_check` على الملف المستبدل = ok.
2. **قراءة Prisma فعلية** (لا sql خام): `user.count / group.count / report.count / workflowHistory.count / auditLog.count` — نجاح الاستدعاءات بحد ذاته يثبت أن Prisma يقرأ الجداول المطلوبة فعلًا.
3. مطابقة counts مع Manifest للنسخة المستعادة — أي فرق يُعرض في التقرير (تحذير لا فشل إن كان الفرق بتحريف صفر — لكن أي فشل قراءة = فشل).
4. فحص fingerprint المخطط = مطابق لما وُضع في تقرير التحقق.

### 10.2 Rollback التلقائي

- شروط التفعيل: فشل أي فحص من 10.1 **بعد** الاستبدال.
- الخطوات: إعادة إنشاء النسخة pre-restore مكان قاعدة التشغيل (نفس آلية التبديل الذري بعد disconnect) + إعادة التحقق عليها (كانت سليمة عند إنشائها) + `RESTORE_ROLLED_BACK` في JSONL وAuditLog (الجديد بعد الاستعادة) + رسالة صريحة للمدير بالنتيجة.
- النسخة التي فشلت لا تُحذف — تبقى في staging كدليل تشخيص (`restored-failed-<ts>.db`) حتى يقرر المشغل.
- **ما بعد النجاح**: النسخة المستبدلة القديمة تبقى `staging/replaced-<ts>.db` حتى نجاح التقرير النهائي ثم تُنقل للنسخ الرسمية بعلامة kind=replaced (أمان إضافي) أو تُمسح بقرار المستخدم — قرار جزئي ضمن D-8.

## القسم 11 — Pre-Restore Backup (إلزامي بلا استثناء)

- يُنشأ **آليًا** داخل `execute` قبل أي تعديل (مرحلة ⑤) بنمط `ifrs-pre-restore-<UTC>.db` + Manifest كامل (kind=pre-restore) — نفس خط إنشاء النسخ اليدوي حرفيًا.
- **لا يوجد أي مسار** (واجهة أو API) ينفذ استبدالًا دون إنشائه أصلًا — لا checkbox تخطي ولا flag سري. فشل إنشائه ⇒ إلغاء الاستعادة كلها قبل الصيانة.
- يظهر في القائمة بعلامة «نسخة ما قبل الاستعادة» — وهو نفسه نقطة الرجوع اليدوي إن اكتشف المشغل مشكلة لاحقًا (نافذة زمنية غير محدودة — النسخ لا تُحذف تلقائيًا في هذه المرحلة، القسم 14).

## القسم 12 — التنزيل والرفع

### 12.1 التنزيل

- `GET /api/backups/[id]/download` — stream مباشر من القرص بـ `Content-Type: application/octet-stream` و`Content-Disposition: attachment; filename="<الاسم الخادمي>"`.
- الحد: صلاحيتان (6.1) + حجم استجابة بلا تحميل كامل في الذاكرة (Bun streams).
- صيغة الحزمة المنزلة (قرار D-1): التوصية **ZIP واحد** يحوي `.db` + `.manifest.json` (أسهل حفظًا ونقلًا للمشغل ويربط الثنائي ببياناته)، مع قبول رفع ZIP أو .db خام. إن فضّل المستخدم ملفين منفصلين يُبسَّط التنفيذ.

### 12.2 الرفع

- `POST /api/backups/restore/validate` — multipart، حد افتراضي **200MB** (متغير `BACKUP_MAX_UPLOAD_MB`)، يُرفض التجاوز بـ 413 قبل القراءة الكاملة (فحص حجم الطلب).
- **لا ثقة باسم الملف إطلاقًا**: يُعاد تسميته فورًا `staged-<randomId>.db` — الاسم الأصلي يظهر فقط كحقل عرض `originalName` (مطهر) في تقرير التحقق.
- فحص النوع بالمحتوى (magic bytes — بند 7 خط 1) لا بالامتداد.
- الملف المرحلي يعيش في staging فقط ويُمسح عند: نجاح الاستعادة، فشل التحقق، أو انتهاء مهلة (غربلة أثناء إنشاء أي نسخة جديدة: staged أقدم من 24h يُمسح — تنظيف عابر لا يمس النسخ الرسمية).
- رفع أثناء وجود staged نشط غير مستهلك: يُستبدل بعد مسح القديم (نموذج واحد نشط كافٍ لنظام بحجم فريق صغير).

### 13.2 ملاحظة password hashes

النسخة تحوي bcrypt hashes (cost 10) — مقاومة استخراج معقولة، لكن الملف يجب معاملته سرًا بحد ذاته (تصنيف الملف في الواجهة: «يحتوي بيانات مالية وهاشات كلمات مرور»).

### 13.3 التشفير at rest — نقاش القرار (D-6)

- **الآن**: يضيف تعقيدًا (إدارة مفتاح، أين يخزن؟ إن في .env المكتوب نفسه فالقيمة الحقيقية منخفضة — من يقرأ القرص يقرأ المفتاح غالبًا) ويؤجل فائدة تتجلى مع النسخ الخارجي (NAS/سحابة).
- **التوصية**: تأجيله لمرحلة لاحقة مرتبطة بالنسخ الخارجي (تشفير AES-256-GCM بمفتاح يُدخل عند النسخ إلى وسائط خارجية، أو `age`/gpg للمشغل)، مع تنفيذ الحواجز المجانية الآن: 0600، خارج public، تنزيل مشفر القناة (HTTPS عبر البوابة). **القرار للمستخدم.**

### 13.4 إجراء الأسرار التشغيلي (خارج النسخة)

- توثيق خطوة يدوية للمشغل: «قبل أي استعادة سيرورة كاملة، احفظ نسخة `.env` في مكان آمن خارج النظام» — والنظام يعرض في الواجهة بصمة الإعدادات `configFingerprint` (بلا قيم) للمقارنة بعد الاستعادة.

## القسم 14 — الجلسات بعد الاستعادة (Session Invalidation)

### 14.1 تحليل الخطر (بند 10 حرفيًا)

- JWT (NextAuth v4, strategy=jwt) يحمل **بصمة الصلاحيات وقت الدخول** (موثق منذ المرحلة 2: «الصلاحيات تختم عند الدخول»). بعد استعادة نسخة أقدم: مستخدم **عُطِّل أو حُذف بعد نقطة النسخ** يظل حامل توكن صالحًا يمر بـ proxy (Edge — يقرأ التوكن فقط بلا DB) ويجتاز فحوص API التي تعتمد الجلسة. **هذا خطر حقيقي معترف به ويجب حجبه إلزاميًا.**
- حالة إضافية: الدخول نفسه يقرأ users من DB المستعادة — كلمات مرور قديمة تعود للصلاحية.

### 14.2 الخيارات والتوصية (قرار D-7)

| الخيار | الآلية | التقييم |
|---|---|---|
| أ) تدوير `NEXTAUTH_SECRET` عند مرحلة Restart | إعادة تشغيل العملية بعد تحديث `.env` بسر جديد عشوائي ⇒ **كل** JWT السابقة تصبح توقيعًا غير صالح فورًا؛ الجميع إلى /login | **التوصية** — أبسط وأقوى إبطال شامل، وتنطبق حرفيًا مع مرحلة ⑨ المسمّاة Restart |
| ب) epoch جلسات في التوكن + مقارنة بقيمة مرجعية | تعقيد إضافي (مصدر الحقيقة يُخزن أين؟ DB المستبدلة ذاتها — ينكسر بالتعريف إلا في ملف خارجي) | يعالج جزئيًا ولا يعالج «مستخدم محذوف يحمل توكنًا» بلا فحص DB لكل طلب |
| ج) فحص DB في jwt callback | يكلف استعلامًا لكل طلب API، ولا يغطي proxy (Edge بلا Prisma) | غير كافٍ وحده |

**شرط تنفيذ (أ)**: `.env` لا يحوي اليوم `NEXTAUTH_SECRET` أصلًا (بصمة dev مشتقة داخليًا) — **يجب تثبيته أولًا** (متطلب 4B، قرار D-10) وإلا فلا يوجد سر محدد نديره، والسلوك الحالي (توليد مشتق قد يتغير بإعادة التشغيل) غير حاكم.

**تجربة ما بعد الاستعادة**: الجميع يُقال لهم «انتهت الجلسة لأسباب أمنية بعد صيانة النظام — سجل الدخول من جديد» — ويعاد توقيع الصلاحيات من DB المستعادة نفسها (وهو المطلوب: الجلسة تعكس حالة القاعدة الجديدة).

## القسم 15 — سياسة الاحتفاظ (Retention) — خيارات للتهيئة، **بلا حذف تلقائي الآن**

بند 11: «لا تحذف Backup تلقائيًا في المرحلة الأولى قبل أن أعتمد السياسة» — **ملتزم به**: تُبنى إعدادات السياسة **كعرض وتهيئة معلنة فقط** (قراءة/كتابة قيم، دون أي منفذ حذف). الحذف اليدوي للمشغل عبر الواجهة يُقيَّد لاحقًا بنفس الموافقة.

| الباراميتر | الافتراضي المقترح | دلالته |
|---|---|---|
| `manual.maxCount` | 10 | حد النسخ اليدوية (عرض تحذيري الآن) |
| `daily.enabled` | false | نسخ يومية (تحتاج مجدولًا — خارجة عن النطاق الآن، انظر D-6/D-8) |
| `daily.maxCount` | 14 | — |
| `preRestore.maxCount` | 3 | حد نسخ ما قبل الاستعادة |
| `retentionDays` | 30 | عمر أقصى للعرض |
| `staging.maxAgeHours` | 24 | **الوحيد المنفذ** — مسح الملفات المرحلية العابرة فقط |

عرض الواجهة: «التقيد بالسياسة سيُفعّل بعد اعتمادك» + شارة على أي نسخة تجاوزت سيادتها. النسخ اليدوية الثلاث الحالية (pre-3.5A + ما يُنشأ) لا تُمس أبدًا (تعليمات المستخدم الصريحة).

**الجدولة المستقبلية للنسخ اليومية** (D-8): آلية مجدول داخل العملية (setInterval مدار) أو مهمة خارجية — تؤجل لتصميمها وقت اعتماد السياسة؛ التصميم لا يفترضها.

## القسم 16 — تأكيد الاستعادة القوي (Restore Confirmation)

بند 14: **لا يكفي Confirm عادي**. حوار الاستعادة قبل execute يعرض:

- اسم النسخة والمعرف، تاريخ إنشائها بالتوقيت المحلي + ISO، الحجم المقروء، checksum مختصر (أول 12 من SHA-256) منشور بجانب الحقل.
- عدّ النسخة: المستخدمون/التقارير/المجموعات/سجل الدورة/التدقيق (من Manifest).
- مدى زمني للبيانات إن توفر (oldest→newest + مدى periodEnd).
- **عدّ الحالة الحالية** المُستبدلة (قبل/بعد جنباً إلى جنب: «ستفقد: N تقريرًا، M مستخدمين حُدثوا بعد النسخة…» — يُحسب من DB الحية قبل الاستبدال).
- حقل إلزامي: كتابة **`RESTORE`** (أو المعرف الكامل للنسخة — يُقبل كلاهما).
- زر التنفيذ معطل حتى: تقرير تحقق سليم + كتابة الكلمة + جلسة **حديثة** (توكن أحدث من X دقيقة — NextAuth يدعم maxAge/تحديث — تفصيل تنفيذي بسيط: إعادة طلب كلمة مرور المشغل في الحوار نفسه كتأكيد ثانٍ، أعلى من مجرد كتابة كلمة).

## القسم 17 — Prisma Migrations: خطة الانتقال من `db push` (إلزامي في التصميم — لا تنفيذ الآن)

### 17.1 الوضع الحالي (مفحوص)

- **لا يوجد مجلد `prisma/migrations` إطلاقًا** — كل التطور تم بـ `db push` (المكشوفة في worklog لكل مرحلة). package.json يحوي سكربتات `db:migrate/reset` غير مستخدمة.
- لا توجد آلية حالية لمعرفة «إصدار المخطط» سوى بصمة الأعمدة (التي قدمها التصميم في القسم 4).

### 17.2 خطة الـ Baseline (تُنفذ مرة واحدة عند الموافقة — ضمن 4B)

1. نسخة احتياطية VACUUM INTO فورية (نمطنا المعتاد) — قبل أي خطوة.
2. توليد SQL المرجعي: `prisma migrate diff --from-empty --to-schema-datamodel prisma/schema.prisma --script` → مراجعة يدوية للمخرج.
3. `prisma migrate dev --name init` على **نسخة مؤقتة من القاعدة الحقيقية** (وليس عليها) لإنشاء مجلد migrations الأول.
4. تثبيت الـ baseline على القاعدة الحالية **دون تطبيق أي SQL** (البنية موجودة أصلًا): `prisma migrate resolve --applied init` — يكتب في `_prisma_migrations` فقط.
5. التحقق: `prisma migrate status` = clean + `prisma migrate diff --from-url db/custom.db --to-schema-datamodel` فارغ (لا drift) + تشغيل سريع للتطبيق.
6. من هنا: **كل تغيير مخطط = migration جديد** (ممنوع `db push --accept-data-loss` في التطوير العادي)، و`schemaVersion` في Manifest يقرأ اسم آخر migration مطبق.

### 17.3 ماذا يمنح هذا الاستعادة

- `_prisma_migrations` داخل أي نسخة تجيب: أي إصدار مخطط هي بالضبط.
- استعادة نسخة أقدم: `migrate deploy` يطبق الفرق المتراكم — **بموافقة صريحة في الواجهة** (سياسة D-3 الخيار ب بعد الاعتماد).
- إنشاء قاعدة جديدة من الصفر: `migrate deploy` على ملف فارغ — إعادة إنتاج حتمية.

### 17.4 المخاطر المعلنة مقدمًا (بند 16: «قبل أن تعرض الخطة ومخاطرها»)

| الخطر | الحجم | التخفيف |
|---|---|---|
| تطبيق init بالخطأ على القاعدة الحية (إعادة بناء جداول) | كارثي لو وقع | التنفيذ على نسخة مؤقتة فقط + resolve --applied لا يشغل SQL + النسخة الاحتياطية في الخطوة 1 |
| drift تاريخي (تعديلات 3.5A عبر سكربتات) لا يطابق init تمامًا | متوسط | migrate diff (from-url) يكشف أي فرق قبل الاعتماد — إن ظهر فرق يُعالج بمigration تصحيحي معروض للمستخدم قبل دمجه |
| بيئة dev بلا shadow db متاح | بسيط | shadowDatabaseUrl مؤقت أو توليد diff خالص بلا dev إن تعذر |
| `db push --accept-data-loss` في سكربت package الحالي يبقى فخًا | بسيط | إعادة تسمية/تعليق السكربت بعد الاعتماد (بموافقة) |

### 17.5 ما لن يفعله هذا القسم

لا يُنفذ أي أمر migrations قبل موافقة المستخدم الصريحة على هذا القسم (D-4). لا يتغير أي سلوك تشغيلي للنظام بعد الاعتماد — البنية الحالية تبقى كما هي، يُضاف فقط سجل إصدارات.

## القسم 18 — Disaster Recovery: النسخ داخل الجهاز مقابل خارج الجهاز

### 18.1 الفرق جوهري لا تفصيلي

| | داخل نفس الجهاز (الوضع الحالي) | خارج الجهاز (Off-device) |
|---|---|---|
| يحمي من | حذف خاطئ، فساد منطقي، خطأ استعادة (بالـ pre-restore) | كل ما سبق **+ تلف القرص + فقدان الجهاز + فساد بيئة العمل كاملة** |
| لا يحمي من | تلف القرص/فقدان الجهاز — **النسخة والبيئة تموتان معًا** | — |

**الدليل الواقعي في هذا المشروع نفسه**: نسخة pre-phase3 وُضعت في `/home/z/backups/` **فُقدت نهائيًا** عند إعادة تهيئة البيئة بينما نجا المشروع من مسار العمل الدائم. أي أن سيناريو «النسخة مع المضيف» وقع فعلًا هنا.

### 18.2 المعمارية المستقبلية المقترحة (بلا تنفيذ سحابي الآن — بند 17)

```
[App/DB] ──VACUUM INTO──▶ [backups/ محلي 0600]
                              │  (مزامنة دورية/يدوية — مرحلة قادمة)
                    ┌─────────┴─────────┐
                    ▼                   ▼
             [NAS/شبكة داخلية]    [وسیعة خارجية يدوية]
             rsync + checksum     نسخة مشفرة (13.3) على قرص خارجي
             verify SHA-256       يفصلها المشغل دوريًا
             + سجل نجاح/فشل
```

- قاعدة التصميم: أي نسخة خارجية **تُتحقق** (قراءة SHA-256 على الوجهة) وإلا فهي لا تُعد نسخة.
- أرصدة العمل الآن: توثيق إجراء يدوي للمشغل («انسخ مجلد backups + سجل الاسترجاع إلى وسيط خارجي أسبوعيًا وقارن الـ hash») + حساب SHA-256 معروض في الواجهة لكل نسخة ليصبح التحقق اليدوي لفظة.
- لا اتصال سحابي في هذه المرحلة (التزام صريح) — التصميم يترك نقطة توسعة واحدة في Backup Service (interface يسمح بوجهات مستقبلية) دون أي كود اتصال.

## القسم 19 — RPO/RTO (توصيات تشغيلية قابلة للتغيير — ليست حقائق مفروضة)

| المؤشر | التوصية المبدئية | الأساس | متى تتحسن |
|---|---|---|---|
| **RPO** (أقصى فقد بيانات مقبول) | **24 ساعة** مبدئيًا | النسخ حاليًا يدوية/قبل تغييرات؛ أقرب جهد تشغيلي واقعي بلا مجدول | عند اعتماد النسخ اليومية (D-8) → 24h مؤكدة؛ مع مجدول ساعي لاحقًا → 1h |
| **RTO** (أقصى زمن لاستعادة الخدمة) | **30 دقيقة** | قاعدة MB: استعادة نفسها ثوانٍ–دقائق؛ الزمن الحقيقي = إدراك المشكلة + وصول المشغل + التحقق + إعادة تشغيل + تسجيل دخول الجميع | الأتمتة الجزئية (الاستعادة من الواجهة) تضغطه فعليًا إلى ~10 دقائق بعد الإدراك |

تصريح أمين: هذه **أهداف إدارية مقترحة** تتحدد بموافقة الإدارة على الإجراء التشغيلي (من ينشئ النسخ ومتى) — النظام يوفر القدرة، والالتزام بقرار تنظيمي. تُراجع بعد أول تدريب استعادة فعلي.
